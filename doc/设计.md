# Minecraft Skin Statue Generator
## Minecraft 皮肤三维雕像生成器技术计划书

**文档版本：** 1.0  
**目标平台：** Windows，Minecraft Java 1.7.10（GTNH 2.9.0）  
**开发语言：** Python 3.11+  
**项目定位：** 本地运行、可视化、小型独立工具

---

## 一、项目目标

开发一个能够将 Minecraft 玩家皮肤 PNG 转换为大型三维方块雕像的本地工具。

程序自动读取皮肤各面的像素颜色，在 Minecraft 原版与本地安装模组提供的可用方块中寻找最合适的材质，生成具有完整立体结构的方块雕像。

用户可以直接在程序内旋转、缩放、观察雕像，切换原始皮肤与实际方块效果，满意后导出为 Minecraft 1.7.10 WorldEdit 可读取的 `.schematic` 文件。

### 核心功能

1. **皮肤读取：** 支持标准 64×64 PNG、旧版 64×32 PNG。
2. **模型解析：** 支持 Steve（Classic）及 Alex（Slim）手臂模型。
3. **皮肤还原：** 支持全部身体表面、独立左右四肢、透明像素与第二层皮肤。
4. **尺寸控制：** 使用整数倍缩放，最高支持 192 格高。
5. **方块匹配：** 根据皮肤像素颜色，匹配目标 Minecraft 实例中真实存在的方块。
6. **实例扫描：** 从本地游戏资源、资源包及模组中构建方块材质索引。
7. **3D 预览：** 实时查看皮肤原始模型和生成后的方块雕像。
8. **材质控制：** 支持排除特定方块、限制材质及重新生成。
9. **结构导出：** 输出兼容 MC 1.7.10 的传统 `.schematic` 文件。
10. **生成报告：** 显示雕像尺寸、方块总量、材料清单和颜色匹配统计。

### 非目标

初始实现不考虑动画、骨骼姿势编辑、服务器插件、跨版本结构转换及自动世界编辑。

项目不需要启动 Minecraft 完成皮肤解析、方块匹配和 3D 预览。

## 二、技术选型

| 组件 | 技术 | 用途 |
|---|---|---|
| 核心语言 | Python 3.11+ | 数据处理及程序逻辑 |
| 图像处理 | Pillow | 皮肤和材质 PNG 读取 |
| 数值运算 | NumPy | 体素数据、颜色批量处理 |
| 颜色匹配 | scikit-image | RGB / Lab 色彩空间转换 |
| 本地服务 | FastAPI | 前后端数据交互 |
| 3D 渲染 | Three.js | 浏览器 WebGL 实时预览 |
| 前端 | HTML / CSS / JavaScript | 操作面板 |
| 结构文件 | nbtlib | NBT 编码及读取 |
| 数据存储 | JSON / SQLite | 方块索引、缓存及配置 |

**技术路线：**

采用 Python 本地服务 + 浏览器界面。

程序启动本地 HTTP 服务，浏览器通过 `127.0.0.1` 访问 UI。Three.js 在浏览器中完成三维显示，Python 负责所有数据生成和文件导出。

前端 JavaScript 库随项目一起打包，不依赖互联网或 CDN。

不需要安装 Minecraft 作为运行依赖，但扫描其材质资源时需要提供实例路径。

### 统一数据模型

程序内部不要直接以 NBT 或 WorldEdit 数据格式存储雕像。

- 坐标 `(x, y, z)`
- 方块调色板索引
- 朝向及 Metadata（如果适用）
- 来源皮肤层（基础层 / 第二层）

方块调色板则记录：

- Registry Name
- Numeric Block ID
- Metadata
- 六个面的纹理
- 六个面的代表颜色
- 材质类别及是否允许使用

使几何生成、颜色匹配、渲染及导出相互独立。

## 四、皮肤解析与几何生成

### 4.1 皮肤 UV 解析

根据 Minecraft 官方皮肤 UV 布局，将 PNG 分解为：

| 身体部位 | 基础层 | 第二层 |
|---|---|---|
| 头部 | Head | Hat |
| 身体 | Body | Jacket |
| 左手 | Left Arm | Left Sleeve |
| 右手 | Right Arm | Right Sleeve |
| 左腿 | Left Leg | Left Pants |
| 右腿 | Right Leg | Right Pants |

每个部位均为长方体，具有 Front、Back、Left、Right、Top、Bottom 六个独立表面。

解析时需要正确处理 UV 坐标的方向、翻转和镜像。

不允许直接将整张 PNG 映射到立方体，否则不同身体部位会出现镜像错误或纹理错位。

对于旧版 64×32 皮肤，自动补全缺少的左右肢体区域，并正确处理旧版镜像规则。

Steve / Alex 模型不能仅凭 PNG 大小可靠判断，提供手动选择，默认 Steve。

### 4.2 几何构建

使用标准玩家模型作为基础几何。

经典模型高度为 32 个纹理单位，完整宽度为 16 个纹理单位。

采用整数放大比例 `S`：

```python
scale = 6
height = 32 * scale
```

支持 `S = 1～6`，生成高度为 32、64、96、128、160 或 192 格的结构。

每个皮肤像素映射为表面 `S × S` 方块区域，并依据身体几何确定厚度、位置和朝向。

初始采用标准站立姿势，双臂自然下垂。

### 4.3 第二层皮肤

第二层必须独立于基础层处理。

生成步骤：

1. 读取第二层的 RGBA 数据。
2. 跳过完全透明像素。
3. 将非透明区域映射至相应部位外表面。
4. 按比例设置相对于主体的外凸偏移。
5. 解决第二层与主体的体素冲突。

对于只有整数坐标的方块结构，使用离散厚度近似原版皮肤的第二层距离。

默认建议第二层在较大雕像上外凸 1 格，并可调整。

不允许为了保持外层而无条件覆盖主体颜色。

半透明像素默认使用 Alpha 阈值转为实体或空缺，因为普通方块无法准确表达任意透明度。

### 4.4 实心与空心

生成器提供：

- 实心雕像
- 空心雕像

空心模式只保留外表面和指定厚度的结构层，避免产生大量不可见的内部方块。

需要保证第二层皮肤和主体结构都正确生成。

## 五、方块资源索引

这是与 GTNH 兼容最密切的模块。

### 5.1 实例资源扫描

用户指定 Minecraft 实例目录。

扫描范围包括：

- 原版 Minecraft JAR
- 当前资源包
- `mods/` 中的 JAR、ZIP
- 其他能够识别的资源路径

读取纹理时，支持 Minecraft 1.7.10 的 `assets/<namespace>/textures/blocks/` 等资源路径。

从 PNG 中计算代表颜色、纹理复杂度及透明度。

扫描完成后缓存结果，避免每次启动都重新读取所有 JAR。

### 5.2 纹理和真实方块的关联

**重要：不能仅凭某张 PNG 存在，就认定它对应可放置方块。**

需要建立真实映射：

```text
Registry Name
    └── Metadata
          ├── Top Texture
          ├── Bottom Texture
          ├── North Texture
          ├── South Texture
          ├── East Texture
          └── West Texture
```

原版方块使用预置映射表。

模组方块优先读取能够可靠解析的模型、配置及注册数据。

对于无法静态解析的动态纹理、多状态机器和特殊渲染方块，不要猜测其方块 ID。

为了完整支持 GTNH，可提供一个可选的 Forge 1.7.10 辅助模组，在游戏内导出运行时的方块注册表、Metadata 状态及实际纹理关联。

该辅助模组只用于生成资源索引，不是雕像生成器的运行依赖。

### 5.3 方块调色板

每种可用方块应包含：

```json
{
  "registry_name": "minecraft:wool",
  "block_id": 35,
  "metadata": 14,
  "textures": {
    "north": "minecraft:blocks/wool_colored_red",
    "south": "minecraft:blocks/wool_colored_red"
  },
  "average_color": [161, 39, 34],
  "color_variance": 12.5,
  "enabled": true
}
```

以上数据仅作结构示例；真实 RGB 和纹理信息应由扫描结果确定。

对于受光照、染色、动态渲染及生物群系影响的方块，无法可靠预测视觉效果时默认排除。

默认排除：

- 空气、流体
- 非完整方块
- 具有复杂 TileEntity 的机器
- 动态模型及特殊渲染方块
- 透明度异常的方块

用户可手动放开限制。

### 5.4 方块注册兼容

MC 1.7.10 使用数字方块 ID 和 Metadata。

模组方块在不同实例或存档中不一定具有相同数字 ID。

因此应将方块的注册名称作为内部稳定标识，并将数字 ID 映射延迟到导出阶段。

导出时支持从目标存档的 `level.dat` 中读取 Forge 注册映射，以目标存档为准完成数字 ID 转换。

找不到准确映射时必须报告错误，而不是随机替换方块。

## 六、颜色匹配算法

### 6.1 基础流程

首先获取皮肤各表面的实际 RGB 颜色。

根据每个表面的朝向，选择可用方块在对应朝向上的纹理颜色进行比较。

不能将方块所有表面简单求平均后统一匹配，因为不同面的颜色可能完全不同。

推荐采用 CIELAB 色彩空间进行颜色距离计算。

计算方式：

```text
皮肤目标 RGB
      │
      ▼
    CIELAB
      │
      ▼
计算候选方块可见面色差
      │
      ▼
加入纹理复杂度惩罚
      │
      ▼
选择总代价最低的方块
```

推荐代价函数：

```text
Cost =
    w1 × ColorDifference
  + w2 × TextureVariance
  + w3 × MaterialPenalty
```

其中：

- `ColorDifference`：ΔE2000 色差
- `TextureVariance`：纹理杂乱程度
- `MaterialPenalty`：不希望使用的材质惩罚

实际运算可先使用 Lab 欧氏距离筛选少量候选，再对候选计算 ΔE2000。

### 6.2 匹配缓存

对皮肤出现的唯一颜色及表面方向进行缓存。

例如：

```python
cache[(rgb, face, palette_version)] = block_state
```

如果多个像素颜色相同，不需要反复搜索整个调色板。

用户修改调色板后，应使相关缓存失效。

### 6.3 纹理一致性

用户可以选择两种优先级：

- **颜色优先：** 尽可能逼近原始皮肤颜色。
- **平滑优先：** 更倾向于颜色均匀的方块，减少视觉噪声。

默认采用平衡模式。

匹配时还需评估其他可能露出的方块表面，避免不同朝向的纹理造成明显接缝。

## 七、3D 实时预览

这是程序的核心交互功能。

### 7.1 预览模式

提供两种可切换的显示模式：

**原始皮肤模式**

直接以 PNG 纹理渲染标准玩家模型，准确展示原始皮肤。

**方块雕像模式**

渲染匹配后的三维方块结构，展示真实的颜色、材质以及第二层皮肤效果。

两种模式使用相同的几何规则，保证对比准确。

### 7.2 交互能力

- 鼠标左键旋转视角
- 滚轮缩放
- 鼠标右键平移
- 重置视角
- 正面、背面、左侧、右侧、顶部视角
- 显示 / 隐藏第二层皮肤
- 显示 / 隐藏地面网格
- 切换原始皮肤与方块模式
- 修改放大比例后重新生成
- 禁用指定方块后重新匹配

界面推荐布局：

```text
┌───────────────────────────────────────────┐
│              Skin Statue Generator        │
├──────────────┬────────────────────────────┤
│              │                            │
│ 皮肤文件     │                            │
│ 模型类型     │                            │
│ 缩放比例     │       3D 预览区域          │
│ 第二层选项   │                            │
│              │                            │
│ 方块资源     │                            │
│ 颜色匹配     │                            │
│ 排除列表     │                            │
│              ├────────────────────────────┤
│ 生成雕像     │  尺寸 / 方块数量 / 状态    │
│ 导出结构     │                            │
└──────────────┴────────────────────────────┘
```

### 7.3 渲染性能

192 格高的雕像可能包含数十万个甚至更多方块体素。

不能简单为每个方块生成独立 Three.js Mesh。

需要采用以下优化：

1. **隐藏面剔除：** 相邻不透明方块之间的面不生成。
2. **Greedy Meshing：** 合并相邻、材质一致的可见面。
3. **材质批处理：** 尽量减少 Draw Call。
4. **异步生成：** 体素计算时不阻塞前端。
5. **缓存几何：** 仅颜色改变时尽可能复用体素几何数据。

预览默认采用实际方块贴图；可增加纯色快速预览，以便观察颜色匹配结果。

所有资源均从本地加载，无需联网。

## 八、Schematic 导出

目标输出为传统 MCEdit / WorldEdit `.schematic` 格式，而不是现代 Sponge `.schem`。

使用 GZip 压缩的 NBT 数据。

核心字段：

```text
Schematic
├── Width
├── Height
├── Length
├── Materials: "Alpha"
├── Blocks
├── Data
├── AddBlocks（需要时）
├── Entities
└── TileEntities
```

按照传统 Schematic 的数组索引规则生成三维结构。

`Blocks` 保存方块 ID 低 8 位；当需要更高位时使用 `AddBlocks`。

`Data` 保存对应 Metadata。

必须严格验证：

- 三维尺寸与数组长度一致
- 数据坐标方向正确
- 方块 ID / Metadata 有效
- 未使用无法映射的模组方块
- 导出后能够重新读取
- 重新读取结果与内部体素数据一致

### 兼容性要求

- 默认采用 MC 1.7.10 支持的方块 ID 与 Metadata。
- 优先兼容该版本的 WorldEdit 6。
- 对模组方块使用目标存档的注册映射。
- 保留一份结构生成报告，方便排查无效方块。
- 不需要 TileEntity 的雕像方块，原则上不生成 TileEntity。

默认以雕像底部中心为放置参考点，避免粘贴时位置偏差。

## 九、材料统计与结果验证

生成完成后展示：

- 结构宽、高、深
- 总体素数量
- 实际非空气方块数量
- 使用的方块种类
- 各方块的具体数量
- 平均及最大颜色匹配误差
- 无法匹配的颜色数量
- 未成功解析的材质数量

支持将材料清单导出为 JSON 或 CSV。

### 基本测试

至少覆盖：

1. 纯色皮肤：生成正确、各面无偏差。
2. 六面不同颜色皮肤：验证 UV 映射及旋转方向。
3. 不对称皮肤：验证左右手、左右腿没有镜像错误。
4. 透明外层皮肤：验证主体与第二层不会错误重叠。
5. Steve 与 Alex：验证两种手臂宽度。
6. 64×32 旧皮肤：验证旧版镜像转换。
7. 192 格雕像：验证尺寸、性能及数据正确性。
8. 模组方块：验证数字 ID 和 Metadata。
9. Schematic 读回：验证导出结构无损。

在最终兼容性验证时，需要将实际 `.schematic` 文件加载到 GTNH 2.9.0 中，确认游戏中表现与程序预览基本一致。

## 十、实际开发步骤

项目不采用复杂的阶段式管理，按以下顺序完成即可。

### 步骤 1：搭建项目与基本界面

建立 Python 运行环境、FastAPI 本地服务、Three.js 页面。

实现皮肤 PNG 导入、原始模型 3D 显示及鼠标视角交互。

**完成标准：** 可以打开 PNG，在本地浏览器里正确看到可旋转的 Minecraft 玩家模型。

### 步骤 2：实现皮肤到三维体素的转换

实现 UV 解析、Steve/Alex 几何、整数倍放大、第二层结构和实心/空心选项。

此时暂时使用皮肤像素原始 RGB 直接赋予体素表面，不进行 Minecraft 方块匹配。

**完成标准：** 能在预览中显示最高 192 格的完整三维像素雕像，模型结构和皮肤图案正确。

### 步骤 3：实现原版方块匹配

建立 Minecraft 1.7.10 原版方块调色板。

实现纹理颜色提取、颜色距离算法、方块选择与缓存。

将生成的原色体素转换为可放置方块体素。

**完成标准：** 3D 预览能够展示真实方块贴图拼成的雕像。

### 步骤 4：实现 Schematic 导出

将内部体素结构编码为传统 NBT Schematic。

加入数据校验、导出后读回测试及文件保存功能。

**完成标准：** 能将原版方块雕像导入 MC 1.7.10 的 WorldEdit，方向、尺寸和颜色正确。

### 步骤 5：实现本地实例扫描

读取指定 GTNH 实例中的纹理资源及相关方块映射信息。

建立缓存和调色板管理功能。

对于无法确定的模组方块，补充运行时注册信息导出方法。

**完成标准：** 能识别并使用经过验证的 GTNH 模组方块，并正确导出到目标存档。

### 步骤 6：完善交互与优化

补充方块禁用列表、第二层控制、颜色匹配策略、材料清单和预览性能优化。

解决大型模型的渲染卡顿与重新生成时的界面响应问题。

## 十一、实现原则

1. **保持简单。** 优先使用成熟库和明确算法，不引入不必要的框架。
2. **先保证正确性。** 皮肤 UV、方块 ID 和 Schematic 坐标必须通过测试。
3. **预览与导出同源。** 3D 预览必须基于实际导出的体素与方块数据，不能生成两个互不一致的结果。
4. **模块相互独立。** 皮肤解析、体素生成、颜色匹配和导出不依赖前端。
5. **不要猜测模组资源。** 未验证的纹理和方块关联不得直接写入最终结构。
6. **可复用。** 方块调色板与 Schematic 导出模块保留独立调用接口，方便未来扩展图片转建筑等功能。
7. **本地优先。** 所有皮肤、实例扫描、生成及预览操作均在本地完成。

## 十二、最终交付

最终项目应包含：

- 可以直接启动的 Python 程序
- 本地浏览器图形界面
- 可交互的双模式三维预览
- 原版与 GTNH 方块调色板
- 颜色匹配与结构生成器
- MC 1.7.10 `.schematic` 导出器
- 材料清单及错误报告
- 必要的自动化测试
- 简洁的安装与使用说明

**最终验收目标：**

用户提供一张 64×64 Minecraft 皮肤 PNG，选择 GTNH 2.9.0 实例并将比例设置为 6 倍，即可在本地看到最高 192 格的完整方块雕像。

确认预览效果后，程序生成一个能够由 MC 1.7.10 WorldEdit 正确加载的 `.schematic` 文件，且游戏内方块外观与预览尽可能一致。
